## BUG-001: 批量接口添加/删除缺乏原子性——遇首个非法元素中止时已提交元素保留、未处理元素跳过

### 问题描述

6 个批量接口（`addNpuDevices`、`addSwDevices`、`removeDevices`、`addRoutingEntries`、`addAclRules`、`removeAclRules`）在校验与提交时采用单循环"校验→立即提交"模式。当列表中存在非法元素（如 null），循环在首个非法元素处抛 `IllegalArgumentException` 中止，导致：

- **已提交的保留**：前 i-1 个合法元素已通过 `store.addXxx()/removeXxx()` 写入内存，不可逆
- **未处理的跳过**：第 i+1 到 n 个元素从未被遍历
- **接口非原子**：调用方得到"半提交"状态——既非全成功也非全失败

### 根因分析

校验与变更交错在同一 `for` 循环中，没有"先全部校验再全部提交"的两阶段设计，也无回滚机制。

**问题模式（6 个方法共有的结构）**：
```java
for (Element e : collection) {
    if (e == null || e 有非法属性) {   // 校验当前元素
        throw IAE("...");               // 非法→抛异常中止循环
    }
    store.addXxx/removeXxx(..., e);     // 合法→立即提交（已变更内存状态）
}
```

**具体场景示例**：
调用 `addNpuDevices("sn1", [d1, d2, null, d3])`：
- i=0: d1 合法 → `store.addNpuDevice("sn1", d1)` — 已写入
- i=1: d2 合法 → `store.addNpuDevice("sn1", d2)` — 已写入
- i=2: null → 抛 `IAE("device in list must not be null")` — 循环终止
- i=3: d3 — 从未执行 — 跳过

结果：Store 中有 d1、d2，没有 d3。半提交状态。

### 修复策略

采用**预校验+全提交（两阶段）**：

- **阶段1 预校验**：遍历全部元素做合法性校验，发现非法立即抛出异常，此时 Store 尚未被修改
- **阶段2 提交**：全部校验通过后才遍历列表执行 Store 操作

**效果**：保证原子性——要么全成功（校验通过 + 全部提交），要么全失败（校验失败抛异常 + Store 未被修改）。

## BUG-002: planPath src/dest 填入非 NPU 设备返回错误码 1007，文档规定应返回 3002

### 问题描述

`planPath` 的 Step 0（设备判断）中，当 `srcDevice` 或 `destDevice` 填入交换机名（非 NPU 设备）时，代码返回 `TOPO_INCOMPLETE(1007)`，但文档 `基础框架设计.md §9.2 Step 0` 第 4-5 条明确规定：

> **4.** 两个设备类型都必须为 NPU（`DeviceType.NPU`）。
> **5.** 若不是 NPU → 返回错误码 **3002**（`SRC_AND_DST_MUST_BE_NPU`）。

测试设计v3 §7 DS-004 也记录了此冲突：`PathService.planPath:65-67` 仅查 `getNpuDevices().get(...)`，填交换机名返回 `TOPO_INCOMPLETE(1007)`，**永不返回 3002**。

### 根因分析

`PathService.java` 行 72-83 的 Step 0 实现只查 `getNpuDevices()`：

```java
NpuDevice srcNpuDevice = null;
NpuDevice destNpuDevice = null;
if (superNode.getNpuDevices() != null) {
    srcNpuDevice = superNode.getNpuDevices().get(request.getSrcDevice());
    destNpuDevice = superNode.getNpuDevices().get(request.getDestDevice());
}
if (srcNpuDevice == null || destNpuDevice == null) {
    return new PathPlanResult(PlanStatus.TOPO_INCOMPLETE, "...");
}
```

**无法区分两种场景**——交换机名在 `swDevices` 中存在但不在 `npuDevices` 中，`getNpuDevices().get(swName)` 返回 `null`，与真正不存在的设备名行为一致，导致代码统一返回 `TOPO_INCOMPLETE(1007)`。

| 场景 | 文档规定返回 | 代码实际返回 |
|------|-------------|-------------|
| 设备名不存在（不在任何设备表中） | `TOPO_INCOMPLETE(1007)` | `TOPO_INCOMPLETE(1007)` ✅ |
| 设备名存在但不是 NPU（是 SW） | `SRC_AND_DST_MUST_BE_NPU(3002)` | `TOPO_INCOMPLETE(1007)` ❌ |

### 修复策略

以文档为准。Step 0 拆为两层判断：

1. **第一层：设备是否存在于 SuperNode** — 用 `getAllDevices()`（合并 npuDevices + swDevices）查找
   - 不存在 → `TOPO_INCOMPLETE(1007)`，消息："Source or destination device not found in topology: <deviceName>"
   - 存在 → 进入第二层
2. **第二层：设备是否为 NPU** — 判断 `device.getDeviceType() == DeviceType.NPU`
   - 不是 NPU → `SRC_AND_DST_MUST_BE_NPU(3002)`，消息："Source or destination must be NPU device: <deviceName> is <deviceType>"
   - 是 NPU → 转为 `NpuDevice` 继续 Step 1

### 涉及文件与方法

| 文件 | 改动位置 |
|------|----------|
| `PathService.java` | Step 0 设备判断逻辑（行 72-85） |

`PlanStatus.SRC_AND_DST_MUST_BE_NPU(3002)` 已存在于枚举定义（`PathPlanResult.java:37`），无需新增。

## BUG-003: routePhase 路由不可达时返回错误码 1009，文档规定应返回 1010

### 问题描述

`planPath` 的 Step 8~12（路由查找阶段）中，当中间设备的路由不可达（LPM 未命中或路由条目无出端口）时，`routePhase` 抛 `RuntimeException("ROUTE_NOT_REACHABLE: ...")`，该异常被 `planPath` 的 `catch(Exception)` 统一包装为 `TOPO_CONNECTION_NOT_FOUND(1009)`，但文档 `基础框架设计.md §9.5/§9.7` 规定路由不可达应返回 `ROUTE_NOT_REACHABLE(1010)`。

测试设计v3 §7 DS-003 也记录了此冲突：`PathService.routePhase:234-243` 抛 `RuntimeException("ROUTE_NOT_REACHABLE: ...")`，被 `planPath:167-170` 的 `catch(Exception)` 包装为 `TOPO_CONNECTION_NOT_FOUND(1009)`。

### 根因分析

`routePhase` 方法（行 265-332）中共有 4 处 `RuntimeException` 抛出点：

| 行号 | 异常消息 | 场景 |
|------|----------|------|
| 272 | `"TOPOLOGY_NOT_FOUND: <superNodeName>"` | SuperNode 不存在（理论上不应发生，Step 0 已检查） |
| 281 | `"DEVICE_NOT_FOUND: <deviceName> in <superNodeName>"` | 中间设备在拓扑中找不到 |
| 309-310 | `"ROUTE_NOT_REACHABLE: no route for device <device> to target <cna>"` | LPM 未命中路由 |
| 316-317 | `"ROUTE_NOT_REACHABLE: no outPort for device <device>"` | 路由条目无出端口 |

`planPath` 方法中存在两处 `catch(Exception)`：

1. **行 222-230**：包裹 `resolveMultiHopPath` → 捕获所有 `Exception` → 返回 `TOPO_CONNECTION_NOT_FOUND(1009)`
2. **行 236、250**：`routePhase` 调用**没有 try/catch**

**问题**：`routePhase` 抛 `RuntimeException`，而 `RuntimeException` 无法携带 `PlanStatus` 语义信息。调用方无法区分"路由不可达"和"路径构建失败"——两者都被同一 `catch(Exception)` 吞成 `TOPO_CONNECTION_NOT_FOUND(1009)`。

### 修复策略

将 `routePhase` 的 `RuntimeException` 替换为已有的 `PathPlanException`，携带对应的 `PlanStatus`，使调用方可以区分不同错误类型并返回正确的错误码。

**异常类型映射**：

| routePhase 场景 | 替换后 PlanStatus | 错误码 |
|------|-------------|------|
| TOPOLOGY_NOT_FOUND | `TOPO_NOT_FOUND` | 1012 |
| DEVICE_NOT_FOUND | `TOPO_CONNECTION_NOT_FOUND` | 1009 |
| ROUTE_NOT_REACHABLE（无路由） | `ROUTE_NOT_REACHABLE` | 1010 |
| ROUTE_NOT_REACHABLE（无出端口） | `ROUTE_NOT_REACHABLE` | 1010 |

**调用方处理**：在 `planPath` 中对 `routePhase` 的两次调用（前向 + 反向）包裹 `try/catch(PathPlanException)`，捕获后直接返回 `PathPlanResult(exception.getStatus(), exception.getMessage())`。`resolveMultiHopPath` 的 `catch(Exception)` 保持不变。

### 涉及文件与方法

| 文件 | 改动位置 |
|------|----------|
| `PathService.java` | `routePhase` 方法（行 265-332）：4 处 `RuntimeException` → `PathPlanException` |
| `PathService.java` | `planPath` 方法（行 236、250）：`routePhase` 调用增加 `try/catch(PathPlanException)` |
