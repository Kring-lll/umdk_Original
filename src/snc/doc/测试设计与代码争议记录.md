### B-1. SNCConfig 没有 logLevel 字段 ⚠️ 关键冲突

| 项 | 值 |
|---|---|

### B-2. Logger 无级别过滤机制 ⚠️ 关键冲突

| 项 | 值 |
|---|---|
| 测试设计说法 | §5.1 用例 `init_warning_level`："logLevel 生效，INFO 被原生过滤" |
| **代码实际** | `Logger.java` 的 `log()` 方法直接调用 `callback.log(level, msg)`，**无任何级别阈值过滤**。所有 DEBUG/INFO/WARN/ERROR 均透传给 LogCallback，过滤责任在调用方提供的 LogCallback 实现 |
| **影响** | `init_warning_level` 用例的预期完全错误：不存在"WARNING 过滤 INFO"的行为 |
| 争议性质 | Logger 设计为全级别透传，测试设计误以为有内部级别控制 |
| 处理建议 | 删除 `init_warning_level` 用例；或改写为测试"LogCallback 注册后所有级别消息均到达 callback" |

### B-3. routePhase RuntimeException 未被 planPath 捕获 ⚠️ 关键冲突

> 此条对 DS-003 的修正，因影响程度重大单独列出

| 项 | 值 |
|---|---|
| 测试设计说法（DS-003） | routePhase 抛 RuntimeException，被 `planPath:167-170` 的 catch(Exception) 包装为 `TOPO_CONNECTION_NOT_FOUND(1009)` |
| **代码实际** | PathService.planPath 的 try-catch **仅包裹 resolveMultiHopPath**（line 203-212）。`routePhase` 调用（line 217 正向、line 231 反向）在 try-catch **之外**，其 RuntimeException **直接向上传播**，不被任何 catch 捕获 |
| **影响** | 1. DS-003 的描述有误；2. `func_path_route_not_reachable` 和 `func_path_route_output_ports_empty` 用例的预期 `=> STATUS(TOPO_CONNECTION_NOT_FOUND, ...)` **与实际不符**——实际会抛未捕获 RuntimeException；3. 调用方（SNCServiceImpl.planPath）也没有 catch，最终异常暴露到调用方 |
| 争议性质 | **代码缺陷 + 测试设计错误**——两边都有问题 |
| 处理建议 | **首选修正代码**：在 planPath 多跳分支中为 routePhase 调用添加 try-catch，将 RuntimeException 包装为 `PathPlanResult(TOPO_CONNECTION_NOT_FOUND, ...)` 或更精确的 `ROUTE_NOT_REACHABLE(1010)`；**次选修正测试设计**：将这两个用例的预期改为 `=> THROW(RuntimeException, "ROUTE_NOT_REACHABLE")` |

### B-4. uninit 不注销 LogCallback

| 项 | 值 |
|---|---|
| 测试设计说法 | 无提及 |
| **代码实际** | `Logger.callback` 是 `static volatile` 字段。`init()` 注册后全局生效，`uninit()` **不调用** `Logger.registerLogCallback(null)` 或类似注销操作。uninit 后 LogCallback 仍然注册，后续 init 不会覆盖旧 callback 除非新 config 提供了不同的 callback |
| **影响** | 1. `func_reinit_recover` 用例：uninit→init 后旧 LogCallback 仍在，若新 init 的 config.logCallback 不同，则需显式覆盖；2. 多实例场景下 LogCallback 是共享的 static 字段，可能互相干扰 |
| 争议性质 | 设计遗漏——uninit 应清理 static callback |
| 处理建议 | 1. 在 uninit 中添加 `Logger.registerLogCallback(null)` 注销；2. 或在测试设计中明确 LogCallback 的 static 生命周期语义 |

### B-5. init(null) 的实际机制与测试设计描述不同

| 项 | 值 |
|---|---|
| 测试设计说法 | §5.1 用例 `init_null_config`："config=null 跳过 setLevel，仍建实例" |
| **代码实际** | init(null) 跳过的是 `LogCallback 注册`（因为 `config != null && config.getLogCallback() != null` 为 false），而非 "setLevel"。代码中没有 setLevel 逻辑。**结果相同**（init 成功，state=READY），但**机制描述错误** |
| **影响** | 用例预期结果仍正确，但注释/描述需修正 |
| 处理建议 | 修正用例描述为 "config=null 跳过 LogCallback 注册，仍建实例" |

### B-6. SNCServiceImpl 重复 init 的行为描述不够精确

| 项 | 值 |
|---|---|
| 测试设计说法 | §5.1 用例 `init_repeat_rebuild`："重复 init 重建（非幂等）"，旧 Store/Engine 丢弃 |
| **代码实际** | 重复 init 会创建**新的** SuperNodeStore/AclStore 并调用 `.init()`，但**旧的 Store 对象未被 `.clear()`**——只是引用被新对象替换。旧 Store 的 ConcurrentHashMap 仍存在于堆中直到 GC 回收。此外 `Logger.callback` 不会被重置（static 字段） |
| **影响** | 非幂等重建描述基本正确，但缺少对旧 Store 内存泄漏风险的说明 |
| 处理建议 | 如果需要严格重建，应在重复 init 前先 clear 旧 Store（类似 uninit 的做法），或明确文档说明旧数据靠 GC 回收 |

## F. 修正建议汇总

### F-1. 代码修正（建议优先实施）

1. **PathService.planPath 多跳分支**：为 routePhase 调用添加 try-catch，将 RuntimeException 包装为 PathPlanResult
   ```java
   // 当前：routePhase 直接调用，异常未捕获
   // 建议：
   try {
       routePhase(multiHopPath, forwardTarget, request.getSuperNodeName());
       // ... reverse phase ...
       routePhase(reversedPath, reverseTarget, request.getSuperNodeName());
   } catch (RuntimeException e) {
       return new PathPlanResult(PlanStatus.ROUTE_NOT_REACHABLE, e.getMessage());
   }
   ```

2. **SNCServiceImpl.uninit**：注销 static LogCallback
   ```java
   Logger.registerLogCallback(null);  // 添加在 uninit 开头
   ```

3. **PathPlanResult 枚举**：移除未使用的 `SRC_AND_DST_MUST_BE_NPU(3002)` 或补全实现

### F-2. 测试设计修正（建议同步实施）
