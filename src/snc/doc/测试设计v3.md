## 2. 通用约定

### 2.1 状态机
```
INIT ──init()──▶ READY ──setSuperNode+setAclData──▶ DATAREADY
  │                │                                    │
  └──uninit()──▶ UNINIT ◀──uninit()────────────────────┘
```
| 状态 | 允许操作 |
|:-----|:--------|
| INIT | `init`、`uninit`；其余方法抛 `SNCStateException("SNC is in INIT state")`（`checkNotUninit` 拦截） |
| READY | 除 `planPath` 外所有方法；`setSuperNode`+`setAclData` 都完成 → DATAREADY |
| DATAREADY | 全部方法；删除任一数据 `superNodeLoaded`/`aclLoaded` 变 false → 回退 READY |
| UNINIT | 仅 `init`；其余方法抛 `SNCStateException("SNC is in UNINIT state")` |

> ⚠️ **planPath 例外**：`planPath` 不走 `checkNotUninit`，自有 `state != DATAREADY` 判断，统一抛
> `"SNC is not in DATAREADY state, current state: <STATE>"`。详见 §7 DS-006。

### 2.2 用例命名规则
- 接口测试：`test_c3snc_pinginner_inter_<语义名>`（全小写、下划线连接）
- 功能测试：`test_c3snc_pinginner_func_<语义名>`（全小写、下划线连接）
- 语义名采用"接口_场景/条件"形式，如 `init_null_config`、`path_same_l1sw_direct`。

### 2.3 期望结果符号
| 符号 | 含义 |
|:-----|:-----|
| `=> VOID` | 正常返回无值 |
| `=> NULL` | 返回 `null`（非异常） |
| `=> THROW(<异常类>, "<msg 子串>")` | 抛指定异常，msg 含子串 |
| `=> STATUS(<PlanStatus>, "<errMsg 子串>")` | planPath 返回该状态，errorMessage 含子串 |
| `=> STATE(<STATE>)` | 调用后内部状态迁移至 STATE |

### 2.4 通用 Setup / Teardown
```java
@BeforeEach void standardSetup() {
    this.sut = new SNCServiceImpl();          // INIT
    this.sut.init(new SNCConfig(Level.INFO)); // INIT → READY
}
@AfterEach void standardTeardown() {
    if (this.sut != null) { try { this.sut.uninit(); } catch (Exception ignored) {} this.sut = null; }
}
```
DATAREADY fixture builder（planPath 场景默认已执行，等同"两张表已填入"）：
```java
void enterDataReady(String fixture) {            // fixture ∈ {2npu_1port, 4npu_8port, full_2tier_gpu}
    sut.setSuperNode(TestDataLoader.loadSuperNode(fixture));
    sut.setAclData(TestDataLoader.loadAclData(fixture, fixtureSuperNodeName));
    // state == DATAREADY
}
```

### 2.5 dataRef 引用约定
每条用例通过 `dataRef` 引用 `pinginner测试数据.json` 中的入参/期望条目，表格只给出可评审的**构造逻辑**与**关键值**。

### 2.6 异常值/特殊字符约定（本版新增）
代码仅做 `null`/`isEmpty()` 校验，**不做任何特殊字符/格式/长度/安全过滤**（仅 EID/CNA 在 planPath 内有正则校验）。故异常值测试覆盖以下取值集合 V：
| 取值类 | 代表值 | 含义 |
|:------|:------|:-----|
| V1 特殊符号 | `"%￥#@!&*"` | ASCII+CJK 符号混合 |
| V2 空白串 | `"   "`（3 空格） | `isEmpty()` 返回 false → 通过校验被存入 |
| V3 超长串 | 256 字符 `a..a` | 无长度上限校验 |
| V4 注入式 | `"'; DROP TABLE sn; --"`、`"<script>x</script>"` | 无安全过滤 |
| V5 Unicode/emoji | `"测试超节点-😀"` | 无编码校验 |
| V6 数字/混合 | `"123-abc.gpu_0"` | 合法风格对照 |

## 3. 真实业务拓扑与数据策略（planPath 场景基准）

> 依据：`主成功场景说明.md`、生产部署形态。**数据文件较大不内联读取**，本设计按"两张表默认已加载"组织 planPath 场景。

### 3.1 拓扑形态
```
        ┌────────────── L2 交换机 (l2sw0 / lc#0) ──────────────┐   ← 顶层，无 EID
   ┌────┴──────┬──────────┬────────────┬─────────────┐
┌──┴──┐     ┌──┴──┐    ┌──┴──┐     ┌──┴──┐
│L1SW0│ ... │L1SW1│ .. │L1SW2│ ... │L1SW3│   ← 中间层，无 EID
└──┬──┘     └──┬──┘    └──┬──┘     └──┬──┘
   │ gpu1..gpuN 每个端口上行至某个 L1SW        ← 底层 GPU/NPU（有 EID/CNA/UPI）
```
**约束**：`planPath` 入参 `srcDevice/destDevice` 只能是 GPU（NPU），因为交换机无 `eid` 可查；
`PathService.planPath` Step 0 用 `superNode.getNpuDevices().get(srcDevice/destDevice)` 查找，填交换机名必返回 `TOPO_INCOMPLETE`（见 §7 DS-004）。

### 3.2 两类典型 GPU↔GPU 路径
| 路径类型 | 链路 | interDevices | hops |
|:---------|:-----|:-------------|:-----|
| 同 L1SW 直达 | gpu1→L1SW0→gpu2 | `{L1SW0: outPort}` | 3 |
| 跨 L2SW 多跳 | gpu1→L1SW0→L2SW0→L1SW1→gpu3 | `{L1SW0:p1, L2SW0:p2, L1SW1:p3}` | 5 |
| 物理直连（罕见/最小用例） | gpuA→gpuB | `null`/`{}` | 2 |

### 3.3 数据修正声明（依据 `主成功场景说明.md §1.2/§1.3`）
`TestDataLoader` 内置只读修正（原始 JSON 不写）：
| 设备 | 原 JSON 路由前缀 | 修正后 | 对应 NPU 端口 CNA |
|:-----|:-----------------|:-------|:------------------|
| l1sw0 | `170.170.170.17/32` | `170.170.170.18/32` | npu1 `400GE 0/0/1`=`170.170.170.18` |
| l1sw0 | `221.221.221.68/32` | `221.221.221.66/32` | npu2 `400GE 0/1/1`=`221.221.221.66` |

#### 6.1.3 test_c3snc_pinginner_func_main_flow_gpu_pairs_100 详述（数据驱动主流程）

> 目标：在主流程贯通的前提下，用**真实两层交换机+GPU 拓扑**的数据驱动覆盖约 100 个 GPU 对，验证 planPath 在大规模组合下的正确性与一致性。

**数据驱动矩阵构造**
- 前置：`init` → `enterDataReady("full_2tier_gpu")`（state==DATAREADY，两张表已加载，具体数据待补充 fixture）。
- GPU 对来源：从已加载 SuperNode 的 `getNpuDevices()` 取全部 GPU 设备名集合 G（|G|≈10~12）。
- 配对方式（目标 ~100 对）：
  | 维度 | 取值 | 组合数（|G|=10 估算） |
  |:-----|:-----|:--------------------|
  | 有序 GPU 对 (src,dst), src≠dst | G×G 去对角 | 10×9=90 |
  | 端口变体 | 每对取 2 个不同 srcPort | ×2 → 上取整至 100 |
  | 路径类型分层 | 同 L1SW 对 / 跨 L2SW 对 | 各占约一半 |
  | 方向 | 正向 + 反向 | 反向已含于"有序对" |

**请求构造逻辑（每条数据）**
```
for (src,dst) in orderedGpuPairs:
  for srcPort in selectPorts(src, k=2):
    dstPort = pickPeerPort(dst, srcPort)           # 与 srcPort 同属一条物理路径的对端口
    inter   = resolveInterDevices(src,srcPort,dst) # 同L1SW→{l1swX:p}; 跨L2SW→{l1swA:p,l2sw0:p,l1swB:p}
    req = PathPlanRequest(superNodeName, src, srcPort, dst, dstPort, inter)
    result = sut.planPath(req)
    assert result.status == SUCCESS
    assert result.srcEid == expectedEid(src,srcPort)
    assert result.dstEid == expectedEid(dst,dstPort)
    assert result.path.hops == expectedHops(src,srcPort,dst,dstPort,inter)
```

**期望（共性）**
- 全部 ~100 对返回 `SUCCESS`；srcEid/dstEid 与拓扑端口表一致；hops 数 = inter.size()+2；中间跳 deviceType=SW，首尾跳 deviceType=NPU。
- state 全程保持 DATAREADY；末尾 `uninit` 后 `=> STATE(UNINIT)`。
