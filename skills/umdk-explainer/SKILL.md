# 代码答疑 Skill（umdk-explainer）

本 skill 用于回答用户对**已有代码库**的提问：函数职责、标识符（变量/参数/字段/宏/枚举）含义、代码片段语义。
**不处理调用关系类问题**（谁调用谁、调用图、调用链）——那归 `umdk-callgraph` skill，见"与其他 skill 的边界"。

**覆盖范围**：`umdk/` 目录下的用户态开发包（URMA / URPC / DLock / UMS / CAM 五大组件，及工具、示例、文档）。

方法论对任意 C 代码库通用——框架相关知识被隔离在 [profile.md](references/profile.md) 一处。

## 何时使用

在以下情况触发本 skill：

- 用户**贴出代码片段**或**选中 IDE 中的文件/行**，问"这什么意思 / 在干什么 / 为什么这么写"。
- 用户问某个**函数/结构体/枚举/宏**的作用或定义位置。
- 用户问某个**参数或变量**的含义、取值范围、为何要传它。
- 用户问"X 在哪个文件 / 哪里定义 / 哪里被使用"。
- 用户问某个**模块/子系统**的职责或边界。

**不触发本 skill**（转交 `umdk-callgraph`）：

- 用户问**调用关系**："谁调用了 X"、"X 调用了什么"、"X 的调用链是什么"、"画一下调用关系"、"call graph"。
  这类问题由 `umdk-callgraph` skill 用 Mermaid 图回答，本 skill 不重复处理。

不适用于：写新代码（用框架自带的编码规范 skill）、跑测试、改 bug（除非用户要求解释 bug 根因）。

## 核心原则（不可违反）

1. **接地优先，禁止臆造**。任何关于符号、签名、字段、行为的结论，必须能在代码里定位到具体的
   `file:line`。读不到就说"未在代码中找到"，绝不基于名称猜测语义。
2. **头文件是 API 的最高权威**。函数签名、结构体定义、枚举值以头文件（`.h`）为准；与文档或注释冲突时
   以头文件为准。文档可能过时，头文件是编译器实际使用的契约。
3. **先定位再解释**。回答前先用 Grep/Glob 把符号定位到定义处和声明处，再读实现，最后组织语言。
   不要凭印象作答。
4. **区分"代码事实"与"推理"**。代码直接体现的写"代码表明…"；基于命名约定、调用上下文推断的写
   "推断…"并说明依据；查到文档佐证的写"文档说明…"并给出链接。
5. **回答要可复核**。引用代码用 markdown 链接 `[符号](path#L行号)`，用户能点开核对。

## 答疑工作流

按问题类型选择分支执行。每一步都强调"读了再答"。

### 通用第一步：定位符号

无论哪种问题，先定位。按效率从高到低：

1. **已知精确符号名** → Grep `pattern: "\b符号名\b"`，`output_mode: content`，`-n: true`。先看
   `file:line` 分布，判断是定义、声明、还是调用点。
2. **只知大概**（用户描述功能而非名字）→ 先读 [profile.md](references/profile.md) 的"模块地图"和
   "API 命名约定"，推断可能的前缀/关键词，再用 Grep 模糊搜。
3. **结构体/枚举定义** → Grep `pattern: "typedef struct 符号名"` 或 `pattern: "} 符号名_t;"`。
4. **宏定义** → Grep `pattern: "^#define 符号名"`。

定位到候选 `file:line` 后，用 Read 读取**包含注释的上下文**（结构体往前读 10 行拿注释，
函数往前读 Doxygen 块）。Doxygen `/** ... */` 注释往往直接说明了用途——这是最可靠的语义来源。

### 问题类型 A：函数作用 / 这段代码在干什么

1. 读**头文件中的声明 + Doxygen 注释**（API 层）。多数 UMDK 头函数有 `@param` / `Return` 注释。
2. 读**实现文件中的函数体**（`.c`）。关注：入口校验、关键循环、锁、错误返回路径、调用的下一层函数。
3. 若函数是薄封装（直接转调下层），追踪一层，说明真正干活的在哪。
4. 回答时给出：**职责一句话** + **关键步骤编号** + **涉及的相邻函数** + **file:line 链接**。

### 问题类型 B：参数 / 变量 / 字段含义

1. **函数参数**：读头文件 Doxygen 的 `@param[in]` / `@param[out]` 注释；无注释则读函数体里如何使用它
   （被读？被写？作为长度？作为标识？）反推语义。
2. **结构体字段**：读结构体定义处的**行内注释**（`/* [Public] ... */` 等）。UMDK 习惯用
   `[Public]` / `[Private]` 标注可见性。查 [data-structures.md](references/data-structures.md) 索引。
3. **局部变量**：读赋值处和使用处，结合类型和命名推断。`cnt`/`num` 多为计数，`fd` 为文件描述符，
   `ctx` 为上下文句柄，`ret`/`rc` 为返回码。
4. **宏 / 枚举值**：读 `#define` / `enum` 定义，看注释和命名。枚举值常在 [data-structures.md](references/data-structures.md)
   有整理。
5. **取值范围**：优先找代码里的校验（`if (x > MAX)` 之类）或宏定义的上下限；找不到就说明"代码未显式约束"。

### 问题类型 C：X 在哪里定义 / 被使用

1. Grep 全库，`output_mode: content`，`-n: true`。
2. 按"定义 / 声明 / 使用"三类归类输出。判断依据：
   - 定义：`typedef struct X`、`} X_t;`、返回类型 + `X(` + `{`、`#define X`。
   - 声明：头文件里 `extern` 或无函数体的原型。
   - 使用：其余出现。
3. 每条给 `file:line` 链接。

## 回答规范

### 必做

- **先给一句话结论**，再展开。用户常只想知道"这是干嘛的"，别一上来堆代码。
- **引用代码用 markdown 链接**：`[func()](相对路径#L行号)`。路径相对仓库根。
- **结构体/函数引用标注行号**，让用户能跳转核对。
- **承认不确定**：没读到的、推断的，明确标注。宁可说"未找到"也不编。

### 禁止

- 把文档/注释的描述当成代码事实转述而不读代码。文档可能过时。
- 用"应该是"、"大概是"糊弄——要么读到确定，要么说"未找到，建议检查 X"。
- 大段粘贴源码而不解释。引用关键 3~5 行即可，其余给链接。
- 回答完不落地到 `file:line`。无法定位的结论对用户不可复核，等于没答。

## 与其他 skill 的边界

- 用户问**调用关系 / 调用图 / 调用链 / 谁调用谁** → 转交 `umdk-callgraph`，本 skill 不处理。
  （explainer 管"单个符号是什么"，callgraph 管"符号之间怎么连"。）
- 用户要**写/改代码** → 用框架的编码规范 skill（如 `c-code-standard`），本 skill 只解释不改。
- 用户要**搭示例/跑起来** → 若有 quickstart 类 skill 则转交；否则本 skill 可解释 API 用法但不生成工程。
- 用户要**迁移代码**（如 verbs→urma）→ 用 `verbs-to-urma-converter` 等专用 skill。

## 框架知识加载

回答前若问题涉及 UMDK 特定概念（UB/Jetty/Segment/tp 等）或需要找模块入口，先读
[profile.md](references/profile.md)。它包含：

- 项目一句话定位与分层（当前覆盖 `umdk/` 用户态开发包）。
- **模块地图**：每个子模块的目录、职责、关键头文件、入口函数、文档链接。
- **API 命名约定**：前缀规律（`urma_*` / `urpc_*` / `ubcore_*`）、后缀规律（`_ex` / `_async` / `_batch`）、
  对称命名（`create/delete`、`import/unimport`、`advise/unadvise`、`bind/unbind`、`active/deactive`）。
- **核心概念速查**：UB、UBVA、Segment、Jetty（JFS/JFR/JFC/JFCE）、tp、EID 等的一句话定义与文档锚点。

按需进一步读取 profile 指向的索引文件：
- [api-index.md](references/api-index.md) —— 公开 API 清单（按模块分组，含 file:line）。
- [data-structures.md](references/data-structures.md) —— 核心结构体/枚举/宏的字段含义。
- [call-graphs.md](references/call-graphs.md) —— 已沉淀的典型调用链。**仅作背景参考**（解释函数作用时
  可引用其流程描述辅助说明），不用于生成调用关系图——调用关系归 `umdk-callgraph`。

**只读当前问题需要的文件**，避免一次性引入无关上下文。

## 自我更新

当发现以下情况，提示用户可调用 `umdk-skill-updater` 刷新本 skill 的索引：

- profile/api-index/data-structures/call-graphs 中的符号在代码里已找不到（API 变更）。
- 调用关系类问题被错误地由本 skill 处理（应转交 `umdk-callgraph`）。
- 出现新的公开头文件或新模块目录。
