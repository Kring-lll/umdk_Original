# 答疑方法论（通用，与框架无关）

本文件沉淀"如何在大型 C 代码库里快速定位并解释一个符号"的可复用技巧。
对任意 C/C++ 代码库有效，不依赖 UMDK 特定知识。框架特异内容见 [profile.md](profile.md)。

## 1. 定位符号的搜索词构造

Grep 的 pattern 决定成败。按目标选词：

| 目标 | 推荐正则 | 说明 |
|------|----------|------|
| 函数调用或定义 | `\bNAME\b` | 词边界防子串误匹配（`read` 不会命中 `pread`/`readv`） |
| 函数定义（C） | `^RETTYPE.*\bNAME\b\s*\(` | 返回类型开头 + 名字 + 紧跟左括号 |
| 函数声明（头文件） | 同上但文件过滤 `*.h` 且无 `{` | 声明以 `;` 结尾 |
| typedef 结构体 | `typedef struct NAME\b` 或 `} NAME_t;` | 前者抓开头，后者抓结尾 |
| 宏定义 | `^#define\s+NAME\b` | 行首 define |
| 枚举值 | `^\s*NAME\b` 配合 `\benum\b` 定位 enum | 枚举值通常缩进 |
| 全局变量 | `^(extern\s+)?TYPE\s+NAME\b` | 行首声明 |

注意：
- C 语言函数名常带模块前缀（如 `urma_`、`ubcore_`），全名搜更精确。
- 不确定大小写时用 `-i`，但 C 区分大小写，确认后去掉 `-i` 避免噪声。
- `output_mode: content` + `-n: true` 才能拿到行号用于链接。

## 2. 从一行代码反推语义的检查清单

用户贴了一行代码问"这是干嘛的"，按此顺序查：

1. **认函数名**：拆前缀（模块）+ 词根（动作）+ 后缀（变体）。例 `urma_import_jetty_async` =
   urma(模块) + import(导入对端资源) + jetty(对象) + async(异步变体)。
   不确定词根含义 → 查 profile 的命名约定。
2. **看返回值**：`urma_status_t` 多为 `0成功/非0错误`；指针类型 `NULL` 表失败；`int` 可能是计数或错误码。
3. **看参数**：`ctx` 上下文句柄必填；`*_cfg` 配置结构体；`*_attr` 属性；`*_t` 多为 opaque 句柄；
   `token` 权限令牌；`rjetty`/`rjfr` 中 `r` 前缀表 remote（对端）。
4. **找注释**：函数上方 Doxygen `/** */`，行尾 `/* ... */`，结构体字段行内注释。
5. **看上下文调用**：这行在哪段逻辑里——资源准备？建链？数据面？错误处理？定位它属于哪一阶段
   （查 profile 的"通信流程阶段"）能快速框定语义。
6. **看被调用函数**：如果这行调了陌生函数，递归定位它，往往下层才是真正干活的地方。

## 3. 追踪调用链的技巧

> 本节用于"解释函数作用时理解它在整体链路中的位置"，**不用于生成调用关系图**。
> 用户若要调用关系图（谁调用谁、call graph），转交 `umdk-callgraph` skill 处理。

### 3.1 自顶向下（从应用 API 追到硬件）

用户问"这个 API 最终怎么落到硬件"：

1. 从用户态公开 API（头文件）出发。
2. 读用户态库实现，找到它如何封装（通常转调同模块内部函数或直接 syscall/ioctl）。
3. 找**系统调用 / ioctl 命令号**的边界：用户态到内核态的过渡点是 `ioctl(fd, CMD, ...)` 或
   `write`/`mmap`。记下 CMD 值。
4. 内核侧在字符设备 `file_operations` 的 `.unlocked_ioctl` / `.compat_ioctl` 里分发 CMD。
   Grep CMD 宏名找到分发函数。
5. 内核侧再往下是驱动 `xxx_ops` 函数指针表，最终落到硬件寄存器/DMA。

每一跳记 `file:line`。链路长时优先沉淀进 [call-graphs.md](call-graphs.md)。

### 3.2 自底向上（从硬件/底层回调追到应用）

用户问"这个回调/钩子谁注册的、何时被调"：

1. 找函数指针注册点：Grep 函数名，看哪里把它赋给 `ops.func = X` 或作为参数传入。
2. 看注册者持有的 ops 表类型，反推调用时机（中断？完成队列？事件？）。
3. 找调用点：Grep ops 表字段名 `.func` 的调用。

### 3.3 横向（同层协作）

问"X 和 Y 什么关系"：

1. 看是否共享同一 `ctx` / `device` / `jetty` 句柄——共享则属于同一通信对象的生命周期。
2. 看 `create` 顺序与 `delete` 逆序，反映依赖关系（被依赖者先创后毁）。
3. 看 `import`/`bind` 把两个对象连起来——这是建链的本质。

## 4. 处理"找不到"的情况

Grep 没命中时，按顺序尝试：

1. **拼写变体**：`jetty`↔`jty`、`create`↔`alloc`、`import`↔`map`、`delete`↔`free`↔`destroy`↔`unimport`。
   框架可能有命名同义词，查 profile 的对称命名表。
2. **前缀不同**：用户说的可能是不带模块前缀的简名，或带了别的模块前缀（跨模块调用）。
3. **宏展开**：真正的符号被宏包裹，Grep 宏名。
4. **在生成的或构建目录里**：`build/` 下的 `.o`/产物不是源码，排除。
5. **条件编译**：`#ifdef` 隐藏了符号，Grep 时注意 `#if` 上下文。
6. **确实不存在**：坦诚告知"未在当前代码库找到 X，可能：(a) 拼写不同 (b) 在未拉取的子模块 (c) 已删除。
   建议用户提供更多上下文。"——**不要编造一个相似名字的函数当答案。**

## 5. 引用代码的链接规范

回答中引用代码统一用 markdown 链接，路径**相对仓库根**：

- 函数：`[func()](path/to/header.h#L行号)`
- 结构体：`[struct_t](path/to/types.h#L行号)`
- 行范围：`[入口](path/to/file.c#L起-L止)`

具体路径、行号、符号名取自当前框架的 profile 与索引（如 `urma_create_jetty` 的真实位置见
[api-index.md](api-index.md)）。示例中的 `func`/`path` 仅为格式占位，不要照抄。

行号取自 Grep 的 `-n` 输出或 Read 的行号前缀。**链接的行号必须真实存在**——编一个不存在的行号
比不链接更糟，因为用户点过去会扑空。

## 6. 何时该沉淀（触发自我更新）

答完一个问题后，若满足任一条件，建议用户调用 `umdk-skill-updater`：

- 花了 ≥3 次 Grep/Read 才定位的符号 → 值得进 api-index 或 data-structures，下次省时间。
- 发现 profile 描述与代码不符（API 变更）→ 需刷新索引。
- 用户问调用关系、本应转交 `umdk-callgraph` 却误由本 skill 处理 → 提示转交。
  （调用链本身的沉淀由 callgraph skill 负责，不在此处。）
- 反复被问的同一概念 → 进 profile 的概念速查。
