# 提取模式（通用，与框架无关）

本文件定义"从 C 代码库提取哪些符号、用什么 Grep pattern、如何组织进索引文件"的可复用规则。
对任意 C 代码库有效。框架特异的目标文件清单与采集锚点见 [profile.md](profile.md)。

## 1. 提取公开 API（→ api-index.md）

### 1.1 识别 API 源头

API 的权威来源是**对外暴露的头文件**，不是 `.c` 实现。识别方法：

- 通常在 `include/` 目录下，或文件名带 `api`/`types`（如 `urma_api.h`）。
- 用 `extern "C"` 包裹、有 Doxygen `/** */` 注释、函数声明以 `;` 结尾（无 `{`）。
- 非公开的内部头文件（如 `*_internal.h`、`*_private.h`、`*_inner.h`）不采。

### 1.2 Grep 函数签名

C 函数声明形态多样，用一个组合正则覆盖：

```
pattern: ^(?:extern\s+)?(?:static\s+)?(?:inline\s+)?[\w\s\*]+\bFUNC_NAME\b\s*\(
```

但采集**全量 API**时不按名字搜，而是按"行尾是 `;` 且含 `(` 的函数原型"批量抓：

```
pattern: \w+\s+\*?\w+\s*\(.*\)\s*;
glob: **/*.h
output_mode: content
-n: true
```

再过滤掉 `#define`、`typedef`、纯变量声明。人工/脚本分类成模块分组。

更稳妥：按"返回类型行首 + Doxygen 注释块在前"的特征定位公开 API。UMDK 头文件有规范 Doxygen，
可 grep `^urma_status_t ` / `^\w+_t \*urma_` 等返回类型前缀批量抓签名行。

### 1.3 取一句话说明

每个 API 的一句话来自其**上方 Doxygen 注释的第一行**（`/** 描述...`）。Grep 命中签名行后，
用 Read 往前读 10~15 行拿 Doxygen 块，提取首行描述。

无 Doxygen 的，从函数名按命名约定拆解（前缀=模块、词根=动作、后缀=变体），写"（按命名推断）"标注。

### 1.4 行号

用 Grep `-n` 输出的行号，作为 markdown 链接的 `#L行号`。

## 2. 提取结构体/枚举/宏（→ data-structures.md）

### 2.1 结构体

```
pattern: ^typedef struct \w+   # 开头
# 或
pattern: ^\} \w+_t;             # 结尾（拿名字）
```

逐个 Read 定义段，提取：
- 结构体名 + typedef 别名 + 起止行号。
- 字段：读行内注释 `/* ... */`，UMDK 习惯标注 `[Public]` / `[Private]`。
- 一句话用途：来自结构体上方注释或字段注释综合。

### 2.2 枚举

```
pattern: ^\s*typedef\s+enum\b
```

提取枚举名 + 各枚举值（行尾注释常说明含义）。

### 2.3 宏

```
pattern: ^#define\s+\w+
```

只采**有语义价值**的宏（如常量上限 `MAX_*`、标志位 `*_FLAG_*`、版本号），跳过纯包装宏。

## 3. 提取调用链（→ call-graphs.md）

### 3.1 入口选择

优先沉淀**用户高频问的**或**跨 ≥3 文件**的链路。从哪一端开始追：

- 自顶向下：从公开 API（头文件）出发，追到内核/硬件。
- 自底向上：从回调/ops 注册点出发，追到调用者。

### 3.2 逐跳定位

对当前函数，Grep 其函数体内的调用：

```
pattern: \b被调函数名\b\s*\(
path: 当前函数所在文件
output_mode: content
-n: true
```

每跳记录：函数名 + 文件 + 行号。链路长时分层（用户态→内核态边界用 ioctl/syscall 标出）。

### 3.3 行号校验

调用链的行号取**调用点**（不是定义点）。用 Grep `-n` 的调用行。

### 3.4 失败处理

某跳找不到（函数被宏包裹、或跨模块间接调用通过 ops 表）：

- ops 表间接调用：找 `ops->func()` 的注册点（`.func = X`）和调用点（`ops->func(...)`）。
- 宏包裹：grep 宏名看展开。
- 实在追不动：标注"↓ 经 ops 表分发，具体实现取决于驱动注册"，不再硬追。

## 4. 提取模块地图/概念（→ profile.md）

### 4.1 模块地图

```
# 目录结构
find <repo> -maxdepth 3 -type d   # 或用 ls
# 每模块的关键头文件
glob: **/include/**/*.h
```

每个模块填：目录 → 职责（一句话） → 关键头文件 → 入口（main/module_init/file_operations）→ 文档链接。

### 4.2 命名约定

采样一批函数名，归纳前缀（模块）、后缀（变体）、对称命名（create/delete、import/unimport…）。
通用对称表见 explainer 的 [profile.md](../umdk-explainer/references/profile.md) §4.3，本框架特异的补充于此。

### 4.3 概念速查

从文档目录（`doc/ch/`）的术语章节提取一句话定义。每个概念：名称 → 定义 → 文档锚点（章节号）。

## 5. 比对与合并策略

更新已有索引文件时：

1. 解析现有文件的表格，提取 `(符号, 行号)` 对。
2. 新采集得到 `(符号, 新行号, 新描述)`。
3. 三态合并：
   - 符号在两边都有：更新行号/描述（描述以新采集为准，除非原描述明显更详尽且仍准确）。
   - 只在新采集：追加。
   - 只在旧文件：用 Grep 验证符号是否还在代码；不在则删除；在但行号变则更新。
4. 保留非表格的人工内容（链路骨架注释、"待补充"段、变更记录）原样。

## 6. 行号链接校验清单

写入前对每个 `#L行号` 抽检：

- Read 该文件该行，确认内容是目标符号（不是偏移到相邻行）。
- 路径相对仓库根，无 `../` 越界。
- 行号 ≤ 文件总行数。

抽检失败率 >5% 时，停止更新并报告"行号采集逻辑可能有系统性偏差，需人工介入"。
