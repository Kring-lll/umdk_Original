# 192 容器 / 8-EID 全局跨 Namespace 共享 — 需求设计与风险分析

> 场景：每节点部署 192 个容器（192 个独立 netns）；每个 `ubcore_device` 仅配 8 个 EID（1 primary + 7 port），属一维 FullMesh；聚合设备数（≤8）远少于容器数（192）。
> 诉求：支持 `ubcore_device` 与 EID **按全局跨 namespace 共享**，让 192 个容器复用同一份 device/EID。
> 本文件合并"需求设计"与"bonding_dev 并发 context 风险分析"两部分：先讲现有共享机制套用到此场景的新增诉求（§1-§8），再深入验证 192 并发 context 的真实瓶颈与风险（§9-§11），最后给实施路径与验证用例。
> 基于源码走读，所有结论带 `file:line` 可回溯。

---

## 1. 场景建模与关键数字

### 1.1 拓扑语义（来自代码）

- 拓扑结构 `ubcore_topo_node.type = 0` = **1D-fullmesh**（[ubcore_topo_info.h:47](01_kernel/drivers/ub/urma/ubcore/ubcore_topo_info.h#L47)）。
- `IODIE_NUM = 2`（2 chip/UE），每 UE 1 primary_eid + 9 port_eid（[:20-31](01_kernel/drivers/ub/urma/ubcore/ubcore_topo_info.h#L20)）。
- `links[IODIE_NUM*PORT_NUM]` = 18×18 连通矩阵（[:55](01_kernel/drivers/ub/urma/ubcore/ubcore_topo_info.h#L55)）。
- 聚合设备 `ubcore_topo_agg_dev` = `{ agg_eid; ues[IODIE_NUM=2] }`（[:35-38](01_kernel/drivers/ub/urma/ubcore/ubcore_topo_info.h#L35)）。

> 本场景"8 个 EID = 1 primary + 7 port"是 9 port 的子集（实际端口数 ≤ PORT_NUM=9），语义一致：少量 EID + FullMesh 直连。

### 1.2 关键数字对照

| 维度 | 数值 | 与现有机制的关系 |
|---|---|---|
| 每节点容器数 | **192** | 192 个独立 netns，需 pernet init 为每个 device 建 192 份 sysfs ldev 副本 |
| 每 device EID 数 | **8**（1+7） | `max_eid_cnt` 远小于 192（文档限额每 ns 每 dev 80 EID） |
| 聚合设备数 | **≤8** | 远 < 192 容器 → **必须共享**，无可能每容器独占 |
| 共享模式 | `dev_sharing=on` + `eid_sharing=on` | 现有三机制可直接启用 |
| 单 device 并发 context | 192 | 所有容器指向同一 device/EID，并发建 context。bonding 模式下每容器 1 v_ctx + ≤8 p_ctxs，约 1728 个底层 context（见 §9） |

### 1.3 核心矛盾

8 个 EID 要被 192 个容器**同时**使用做 FullMesh 通信。现有共享机制解决的是"可见性 + 访问放行"，但**没有解决"8 个 EID 如何被 192 个容器并发复用"的资源映射问题**——这才是本场景的新增诉求核心。

## 2. 现有共享机制能直接覆盖什么、覆盖不了什么

### 2.1 现有机制直接覆盖（无需改动）

| 需求 | 现有机制 | 证据 |
|---|---|---|
| 192 容器都能"看到"同一 device | 机制②：shared 模式下 pernet init 为每个 ns 建 sysfs ldev 副本 | [ubcore_device.c:2522](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2522) |
| 192 容器都能"通过"访问校验 | 机制①：`g_dev_ns_shared`/`g_eid_ns_shared` 短路 `dev_accessible`/`eid_accessible` | [ubcore_device.c:1686,1572](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L1686) |
| 192 容器都能看到全部 8 个 EID | `uburma_fill_eid_list`/`eid_show_cb` 在 `eid_ns_shared` 下不过滤 | [uburma_cmd.c:4083](01_kernel/drivers/ub/urma/uburma/uburma_cmd.c#L4083) |
| 容器 netns 增删自动维护副本 | 机制③：pernet init/exit | [ubcore_device.c:2522,2480](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2522) |

### 2.2 现有机制覆盖不了（本场景新增诉求）

| 问题 | 根因 | 影响 |
|---|---|---|
| **P1 sysfs ldev 副本数爆炸** | 192 netns × N device = 192×N 个 `ubcore_logic_device` kobject + sysfs 节点 | 启动慢、内存占用、netns init 阻塞容器拉起 |
| **P2 字符设备 `/dev` 节点不跨 ns** | uburma/ubagg class 非 netns-aware | 192 容器都要 bind-mount `/dev/uburma/*`，部署成本高 |
| **P3 8 EID 被多容器并发复用，缺映射/调度** | 共享只放行访问，未规定"哪个容器用哪个 EID" | FullMesh 下 192 容器抢 8 个 port EID，可能拥塞/错配 |
| **P4 EID 不绑定调用者 ns 后归属丢失** | `eid_sharing=on` 后 `eid_accessible` 不再比较 `e->net` | 无法区分 EID 被哪个容器用，故障定位/审计难 |
| **P5 cgroup 配额 per-process，单 device 192 并发** | rdmacg 按 task 计费 `HCA_HANDLE`/`HCA_OBJECT` | 单 device 承载 192 容器流量，配额/隔离需重新设计 |
| **P6 FullMesh 路径选择在共享后仍按全局 topo** | `ubcore_get_path_set` 按全局 topo map 选 port | 192 容器都走同一套 8-EID 路径集，无 per-容器 隔离/负载均衡 |
| **P7 netns 销毁时 EID invalidate 影响** | shared+`!eid_ns_shared` 时 `ubcore_invalidate_eid_ns` | 若误切 eid_sharing off，192 容器中任一 ns 销毁会 invalidate EID |

## 3. 细化需求设计

按"必须改内核 / 仅部署侧 / 需配套机制"三类拆解。

### 3.1 需求 R1：共享模式稳定开启与防误切（P7）

**诉求**：192 容器长期运行，`dev_sharing`/`eid_sharing` 必须全程 on，禁止运行期误切 off 导致 invalidate。

**设计**：
- 启用脚本固化：节点初始化时 `urma_admin system set dev_sharing on && eid_sharing on`，写入 systemd unit / 节点初始化 hook，先于任何容器拉起。
- 切换约束已有内核保护：shared→exclusive 需 `g_ubcore_net_list` 空（[:2187](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2187)），192 容器运行时无法切 off（会 `-EPERM`），天然防误切。
- **新增**：监控告警，定期 `urma_admin system show` 校验 `DEV_NS_SHARED`/`EID_NS_SHARED` 均 on，异常告警。

### 3.2 需求 R2：sysfs ldev 副本的可扩展性（P1）

**诉求**：192 netns × N device 的 sysfs 副本不能成为瓶颈。

**现状**：`ubcore_net_init`（[:2551](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2551)）在新 ns 为每个 UB device 调 `ubcore_add_one_logic_device` → `device_create` + `ubcore_fill_logic_device_attr`。192 容器并发拉起时，每个容器 init 要为所有 device 各建一个 kobject，串行持 `g_device_rwsem` 读锁 + `dev->ldev_mutex`。

**设计建议**：
- **容量评估**：每副本 `sizeof(struct ubcore_logic_device)` + 1 个 kobject + N 个 sysfs attr；192×N 需实测内存（预估 MB 级，可接受），但**启动时延**是重点——192 容器顺序 init × 每 device 的 `device_create` 是串行的。
- **并发拉起策略**：容器分批启动（如每批 16），避免 192 个 netns 同时 init 抢 `g_ubcore_net_rwsem` 写锁导致雪崩。
- **内核侧可选优化（需改）**：副本创建改异步化或延迟到容器首次访问 device 时按需建（lazy ldev），减少 netns init 时延。当前 `ubcore_net_init` 即便建副本失败也 `return 0` 不阻断容器（[:2560](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2560)），但副本缺失会让该容器 sysfs 看不到 device。
- **降配额**：若 device 数多，shared 模式下副本数 = netns × UB_device；若 UB_device 恒为聚合后的少量 bonding device（≤8），则副本 ≤ 192×8 = 1536，可接受。**建议容器只用 bonding_dev 聚合口**，不暴露底层每 UE 的物理 device，把 N 压到 ≤8。

### 3.3 需求 R3：字符设备节点跨 ns 分发（P2）

**诉求**：192 容器都要访问 `/dev/uburma/*` 和 `/dev/ubagg`，不能每容器手动 bind-mount。

**设计**：
- **方案 A（推荐）：容器只用 bonding_dev 聚合口**。bonding device 的 EID 固定 `init_net`（[ubagg_ioctl.c:1304](01_kernel/drivers/ub/urma/ubagg/ubagg_ioctl.c#L1304)），全局可见；容器内只需挂载 `/dev/uburma/bonding_dev0` 和 `/dev/ubagg` 两个节点。
- **方案 B：容器 runtime 统一注入**。用 device plugin / daemonset 把 `/dev/uburma/*`、`/dev/ubagg`、`/usr/lib64/liburma*`、`/usr/lib64/urma/` 标准化挂载到所有容器，192 容器零差异。
  ```yaml
  # K8s device plugin 暴露 "urma/bonding_dev" 资源，Pod 声明 requests
  resources:
    requests: { urma/bonding_dev: 1 }
  ```
- **方案 C（需内核改，重）**：让 uburma/ubagg class 也 netns-aware（加 `.ns_type`/`.namespace` 回调），使 `/dev` 节点自动按 ns 归属。改动面大、影响所有场景，不建议为此场景单独做。

### 3.4 需求 R4：8-EID 跨 192 容器的复用与调度（P3、P4、P6）— **核心新增**

**诉求**：8 个 EID（1 primary + 7 port）被 192 容器并发复用做 FullMesh，需明确"谁用哪个 EID、如何不冲突、如何负载均衡"。

**现状**：共享模式只放行访问，**任何容器都能用全部 8 个 EID 的任意一个**。FullMesh 下，源/目的 EID 由应用通过 `urma_import_jetty(rjetty.eid=dst_eid)` 显式指定，内核不分配。**风险**：192 容器都倾向选同一组 primary/port EID，导致某些 port EID 热点、链路拥塞，其余 port EID 空闲。

**设计（分层）**：

#### R4.1 EID 分配策略（应用/编排层，不改内核）
- **静态分片**：把 192 容器按 hash(id) % 7 映射到 7 个 port EID，每 port EID 承载 ~27 容器。primary EID 留作控制/建链用。
- **bonding 多路径**：用 bonding_dev 聚合口（agg_eid），bonding 层自动在 7 个 port EID 间做负载分担（`bondp_datapath_schedule.c`），应用不感知具体 port。**推荐**——天然解决调度。
- **URMA per-container 选路**：应用侧 `urma_get_device_by_eid` 拿到 bonding_dev 后，由 bondp 层选具体 slave/port，避免 192 容器都手写死 primary EID。

#### R4.2 EID 使用可观测（内核侧需增强，P4）
- 现状：`eid_sharing=on` 后 `eid_entries[i].net` 不再参与校验，**无法知道某 EID 被哪些容器/进程用**。
- **新增需求**：为共享 EID 增加 per-EID 的使用计数/活跃 context 计数，暴露到 sysfs 或 genl，供运维查"哪个 EID 被多少容器占用、是否热点"。
  - 实现点：`ubcore_alloc_ucontext` 成功后对 `eid_index` 做 `atomic_inc`，destroy 时 dec；sysfs 新增 `eids/eidN/users` 节点。
- 这不改共享语义，只加可观测性，是本场景运维刚需。

#### R4.3 FullMesh 路径选择（内核侧评估，P6）
- `ubcore_get_path_set`（[ubcore_topo_info.c](01_kernel/drivers/ub/urma/ubcore/ubcore_topo_info.c)）按全局 topo + tp_type 选 primary/port 路径。192 容器共享同一份 topo，选路逻辑一致。
- **需求**：确认共享模式下选路不因 ns 不同而退化（共享后 `ubcore_dev_accessible` 放行，选路应正常）。需做 192 容器并发选路的压测，验证 7 port EID 的负载是否均衡，是否需要内核侧加 per-ns 的轮询/最少占用选路权重。
- **若不均衡**：bonding 层 `bondp_datapath_schedule` 已有 active_indices 调度，优先在 bonding 层解决，不动 ubcore 选路。

### 3.5 需求 R5：单 device 承载 192 容器的资源与隔离（P5）

**诉求**：一台 `ubcore_device` 被 192 容器并发建 context、收发，资源（jetty/jfc/seg/cq 等）与配额能否承受。

**现状**：
- cgroup rdmacg 按**进程**计费 `HCA_HANDLE`/`HCA_OBJECT`（[ubcore_cgroup.c](01_kernel/drivers/ub/urma/ubcore/ubcore_cgroup.c)），192 容器各自在其 cgroup 计费。
- device 内部 `ht[UBCORE_HT_NUM]` hash 表、`use_cnt` 等是全局的，多容器共享。
- 每 device 的 `PING_RECV_DEPTH`/jfc depth 等是 per-context 资源，192 并发会放大。

**设计**：
- **配额模型**：rdmacg 设节点级总配额 = 单 device 硬件上限，再按容器 cgroup 设子配额，防某容器耗尽。
- **资源容量评估**：jetty/jfc/seg 数量上限需 ≥ 192 容器 × 每容器用量；若硬件容量不足，需限制并发容器数或减少每容器资源。
- **故障隔离**：一个容器 crash 释放 context（`ubcore_alloc_ucontext` → `ubcore_cgroup_uncharge`）不能影响其余 191 个。现有 uobj 事务机制（[uburma_uobj.c](01_kernel/drivers/ub/urma/uburma/uburma_uobj.c)）应已保证，需专项测试。
- **隔离需求**：是否需要 per-容器 流控/优先级？若 FullMesh 下某些容器流量大影响他人，需在 bonding 层或 cgroup 层加 per-cgroup 限速。

### 3.6 需求 R6：netns 销毁的稳定性（P1、P7）

**诉求**：192 容器频繁创建/销毁（如滚动更新），netns exit 不能拖垮节点。

**现状**：`ubcore_net_exit`（[:2480](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2480)）shared 模式下删该 ns 的所有 ldev 副本 + 按 `eid_ns_shared` 决定 reset/invalidate EID。删副本持 `g_ubcore_net_rwsem` 写锁 + `g_device_rwsem`。

**设计**：
- 验证 192 容器滚动销毁时，每次 exit 删 N 个副本的耗时与锁持有时长。
- 若 exit 期间阻塞新容器 init（共享 `g_ubcore_net_rwsem`），需限速销毁或异步化。
- **重点**：`eid_sharing` 必须全程 on，否则 exit 走 `ubcore_invalidate_eid_ns`（[:2515](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2515)）会把 EID 标 invalid 影响其余容器——R1 的防误切是前置保障。

## 4. 实施路径（按改动面从小到大）

| 路径 | 改动面 | 内容 | 覆盖需求 |
|---|---|---|---|
| **路径 1：纯部署编排** | 无内核改 | shared 模式固化 + 容器只用 bonding_dev + device plugin 标准化挂 `/dev` + 应用走 bonding 选路 | R1, R3, R4.1, R6 部署侧 |
| **路径 2：+ 可观测性** | 内核小幅 | per-EID 使用计数 + sysfs/genl 暴露 + 告警校验开关 | + R4.2 |
| **路径 3：+ 容量与隔离** | 内核中幅 + 配置 | cgroup 配额模型 + 192 并发压测 + 必要的 per-cgroup 限速 | + R5 |
| **路径 4：+ 性能优化** | 内核大幅 | lazy ldev 副本、exit 异步化、选路 per-ns 权重 | + R2, R6 时延 |

**建议优先级**：路径 1（立即可用，框架层跑通）→ **前置门禁：§11 HW 容量实测（TID/jfc/jetty）** → 路径 2（运维刚需）→ 路径 3（稳定性）→ 路径 4（性能，按压测结果决定是否做）。

> 注：路径 1 能让场景在框架层（ns 可见性 + 访问放行）跑通，但 §10-§11 揭示的 HW 层 TID/jfc/jetty 容量（R-1/R-2）是 192 并发（约 1728 context）的硬门禁，必须先实测确认，否则需调整方案（减并发/扩容/复用）。

| 用例 | 方法 | 预期 |
|---|---|---|
| V1 192 容器可见性 | shared on 后批量起 192 容器，各 `ls /sys/class/ubcore` | 均可见 bonding_dev |

## 6. 风险与未决项（含并发 context 验证结论）

### 6.1 已澄清（原未决项 1）

**bonding_dev 的 `p_ctxs[]`（容量 20）不是 192 并发的瓶颈**（详见 §9-§10）。`URMA_UBAGG_DEV_MAX_NUM=20` = `PRIMARY_EID_NUM(2) + PORT_EID_MAX_NUM(18)`（[urma_ubagg.h:23](00_umdk/umdk/src/urma/lib/urma/bond/include/urma_ubagg.h#L23)），是**单进程** bonding context 在每个 slave EID 上的真实 context 数组上限，与容器数无关。192 容器 = 192 个独立进程 = 192 个各自独立的 `bondp_context_t`，每个内部 `p_ctxs[≤8]`，8 EID 远小于 20，不触限。

### 6.2 真正的风险（来自 §10 并发 context 验证，按严重度排序）

| 编号 | 风险 | 严重度 | 处置 |
|---|---|---|---|
| **R-1** | USVA TID / SVA PASID 耗尽（每 context 占 1 个，192 容器 ≈ 1728 context） | **高·可行性决定项** | 实测 TID 池/PASID 容量，扩容或减并发（§11） |
| R-2 | max_jetty / max_jfc 硬上限（`udma_dev->caps.jetty.max_cnt` 等） | 高 | 实测 caps，必要时减每容器资源 |
| R-3 | `g_seg_tree_mutex` 全局锁竞争（192 并发建链） | 中高 | 压测建链 QPS，必要时改锁 |
| R-4 | 内存线性放大（context 结构 + 页目录 + CQE mmap × 1728） | 中高 | 估算 + 限 jfc depth + 监控 |
| R-5 | cgroup per-process 计费与 HW 全局资源不对齐 | 中 | 节点级总配额 = HW 容量 |
| R-6 | bonding v_ctx 复用但 p_ctxs 仍每 EID 一个 context（1728 真实 context） | 中 | 评估 context 池化复用（跨进程共享需改设计） |
| R-7 | per-mm 绑定（`ctx->mm`）与容器 mm 生命周期，泄漏累积 | 中 | 验证滚动销毁资源回收 |
| R-8 | context 创建失败错误不直观（靠 dmesg `failed to alloc separate pages USVA device` 定位） | 低 | 监控该日志告警 |

### 6.3 其他待测项

1. **`max_eid_cnt=8` 与文档限额"每 ns 每 dev 80 EID"**：共享后 8 EID 全局可见不触发 80 限额，但需确认 `uburma_fill_eid_list` 返回 8 而非按 ns 截断。**低风险**，需实测。
2. **FullMesh 1D 选路在共享下的正确性**：192 容器共享同一 topo map，需确认选路不混淆不同容器路径。**需端到端测试**。
3. **kobject/sysfs 上限**：内核对单 device sysfs 子节点数是否有硬上限，192 副本是否触限。**需实测**。

## 7. 总结

本场景的核心新增诉求不是"能否共享"（现有 `dev_sharing`/`eid_sharing` 三机制已能开），而是：

1. **8 EID 被 192 容器并发复用的调度与可观测**（R4）——现有机制只放行不调度，需补 per-EID 使用计数 + 优先用 bonding 层分担。
2. **单 device 承载 192 并发的资源与隔离**（R5 + §10 风险）——cgroup 配额模型 + **HW 层 TID/jfc/jetty 容量评估**（R-1/R-2 是可行性门禁）+ 故障隔离。
3. **192 netns 的副本/锁可扩展性**（R2/R6）——sysfs ldev 副本数与时延，分批拉起 + 必要时内核 lazy/异步化。
4. **`/dev` 节点分发**（R3）——device plugin 标准化挂载，优先用 bonding_dev 减少节点数。
5. **共享模式防误切 + 开关监控**（R1）——固化启用 + 告警。

落地优先走"路径 1 纯部署编排"即可让场景在框架层跑通，路径 2/3 按运维与稳定性需求推进，路径 4 依压测决定。**但 §10 揭示的 HW 层 TID/jfc/jetty 容量（R-1/R-2）是硬门禁**，必须先实测确认 ≥ 1728 context 的资源容量，否则需调整方案（减并发/扩容/复用）。

# 第二部分：192 容器 bonding_dev 并发 Context 容量与风险分析

> 验证目标：bonding_dev 是否支持 192 容器并发建 context（对应原未决项 1，已澄清）
> 核心结论：**用户态 bonding 层 `p_ctxs[]`（容量 20）不是瓶颈**；192 并发的真正约束在**内核 per-fd context 模型 + HW 层（udma）每 context 占用的 USVA TID/jfc/jetty 等有限资源**。

---

## 9. 概念澄清：`p_ctxs[]` 不是容器并发数

### 9.1 `URMA_UBAGG_DEV_MAX_NUM = 20` 的真实含义

[urma_ubagg.h:23](00_umdk/umdk/src/urma/lib/urma/bond/include/urma_ubagg.h#L23)：

```c
#define URMA_UBAGG_DEV_MAX_NUM        (20)
#define URMA_UBAGG_MAX_CONNECTION     (URMA_UBAGG_DEV_MAX_NUM * URMA_UBAGG_DEV_MAX_NUM)
```

[bondp_types.h:32-34](00_umdk/umdk/src/urma/lib/urma/bond/bondp_types.h#L32)：

```c
#define PRIMARY_EID_NUM               (2)
#define PORT_EID_MAX_NUM_PER_DEV      (9)
#define PORT_EID_MAX_NUM              (PORT_EID_MAX_NUM_PER_DEV * PRIMARY_EID_NUM)  // = 18
```

20 = `PRIMARY_EID_NUM(2) + PORT_EID_MAX_NUM(18)`，即**一个 bonding device 下所有 slave UE 的 primary + port EID 总数上限**。[bondp_types.h:119](00_umdk/umdk/src/urma/lib/urma/bond/bondp_types.h#L119) 的 `p_ctxs[URMA_UBAGG_DEV_MAX_NUM]` 是**单进程** bonding context 在每个 slave EID 上的真实 `urma_context_t` 指针数组。

### 9.2 bonding context 是 per-process，不是 per-container 共享池

`bondp_create_pcontext`（[bondp_provider_ops.c:556](00_umdk/umdk/src/urma/lib/urma/bond/bondp_provider_ops.c#L556)）对每个 member EID 调 `urma_create_context(m->dev, m->eid_index)` 存入 `bdp_ctx->p_ctxs[i]`。`bdp_ctx` 属于**一个进程**的一次 bonding context 创建（`v_ctx` 是 bonding_dev 虚拟 context，`p_ctxs` 是它在每 slave 上的真实 context）。

**所以 192 容器 = 192 个进程 = 192 个各自独立的 `bondp_context_t`，每个内部 `p_ctxs[≤20]`。** `p_ctxs` 容量 20 与 192 无关——它限制的是"一个 bonding_dev 最多挂 20 个 slave EID"，本场景 8 EID（1+7）远小于 20，**不触限**。

> 结论修正：原需求设计"未决项 1"（p_ctxs 容量 20 不够 192）是**误判**。bonding 层无 192 并发障碍。

## 10. 真正的约束链与风险清单

### 10.1 context 是 per-fd，无 per-device context 数上限

[uburma_cmd.c:76-106](01_kernel/drivers/ub/urma/uburma/uburma_cmd.c#L76)：

```c
down_write(&file->ucontext_rwsem);
if (file->ucontext) {  // 每 fd 只能有一个 ucontext
    up_write; return -EEXIST;  // "should not create ctx in same fd"
}
ucontext = ubcore_alloc_ucontext(ubc_dev, eid_index, ...);
file->ucontext = ucontext;
```

内核 ubcore 侧 `ubcore_alloc_ucontext`（[ubcore_device.c:1704-1763](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L1704)）只做：参数校验 → ns 访问校验（`dev_accessible`+`eid_accessible`）→ cgroup 计费 → `dev->ops->alloc_ucontext`（委托 HW 驱动）。**ubcore/uburma 层没有 per-device context 计数**，192 容器各开 fd 各建 context 在框架层都放行。

### 10.2 HW 层（udma）每 context 占用的有限资源 — 真正瓶颈

[udma_ctx.c:141](01_kernel/drivers/ub/urma/hw/udma/udma_ctx.c#L141) `udma_alloc_ucontext` 每个 context 做的事：

```c
ctx = kzalloc(sizeof(struct udma_context), GFP_KERNEL);
ret = udma_get_usva_tid(dev, ctx);   // ★ 申请 USVA TID（有限资源）
udma_set_dtu_va_info(dev, ctx);
ctx->mm = current->mm;              // ★ 绑定当前进程地址空间
INIT_LIST_HEAD(&ctx->pgdir_list);  // per-context 页目录
INIT_LIST_HEAD(&ctx->hugepage_list);
INIT_LIST_HEAD(&ctx->page_list);
udma_init_ctx_resp(dev, udrv_data, ctx->dtu_en);
```

| 资源 | 来源 | 是否 per-context | 192 并发风险 |
|---|---|---|---|
| **USVA TID** | `udma_get_usva_tid`（[udma_ctx.c:83](01_kernel/drivers/ub/urma/hw/udma/udma_ctx.c#L83)）→ `ummu_core_alloc_separate_tdev` 或 `iommu_sva_bind_device_isolated` | 每 context 一个（`ctx->tid`） | **高**：TID 是 ummu-core 全局资源池，有上限；192 各独立 mm → 各需独立 SVA 绑定 |
| `max_jfc` | `dev->caps.jfc.max_cnt`（[udma_main.c:137](01_kernel/drivers/ub/urma/hw/udma/udma_main.c#L137)） | 每 jfc 一个，context 可建多个 | **中高**：192 × 每容器 jfc 数 ≤ max_jfc |
| `max_jetty` | `dev->caps.jetty.max_cnt`（[:138](01_kernel/drivers/ub/urma/hw/udma/udma_main.c#L138)） | 每 jetty 一个 | **高**：建链必需，192 容器每端都要 jetty |
| `max_jetty_grp` / `max_jetty_in_jetty_grp` | [:141-142](01_kernel/drivers/ub/urma/hw/udma/udma_main.c#L141) | — | 中 |
| 页目录/巨页 list | per-context `pgdir_list`/`hugepage_list`/`page_list` | 每 context 一套 | 内存线性放大 |
| CQE 映射 | `dev->caps.cqe_size * jfc.depth`（[udma_ctx.c:283](01_kernel/drivers/ub/urma/hw/udma/udma_ctx.c#L283)） | per-jfc mmap | 192 × depth × cqe_size，内存压力大 |

### 10.3 USVA TID 是最硬的墙

[udma_ctx.c:83-105](01_kernel/drivers/ub/urma/hw/udma/udma_ctx.c#L83)：

```c
static int udma_get_usva_tid(struct udma_dev *dev, struct udma_context *ctx) {
    if (dev->caps.sva_sep_mode_en) {
        ctx->tid = UMMU_INVALID_TID;
        ctx->ummu_dev = ummu_core_alloc_separate_tdev(&opt, &ctx->tid);  // ★ 申请 TID
        ctx->seg_tree = xa_load(&g_seg_tree_table, ctx->tid);  // 全局 seg_tree 表
        ...
    } else {
        iommu_sva_bind_device_isolated(ctx->sva);  // SVA per-mm 绑定
    }
}
```

- `sva_sep_mode_en=true`：每 context 申请一个 TID，来自 `ummu-core` 全局资源池（`g_seg_tree_table` xarray）。**TID 数有硬上限**，192 并发若超池容量，第 N 个 context `ummu_core_alloc_separate_tdev` 返回 NULL → `udma_alloc_ucontext` 失败 → 容器建 context 失败。
- `sva_sep_mode_en=false`（SVA 模式）：走 IOMMU SVA per-mm 绑定，192 容器各有独立 mm 各需一次 SVA 绑定；受 IOMMU/设备 PASID 容量限制。

> **这是 192 并发能否跑通的决定性未知**：TID 池容量 / SVA PASID 容量必须 ≥ 192 × 每容器 context 数（bonding 模式下每容器 1 v_ctx + ≤8 p_ctx = 最多 9 context/容器，192×9=1728）。

## 11. 关键容量公式与待测项（可行性门禁）

192 容器 bonding 模式下的底层资源需求：

```
context 总数 = 192 容器 × (1 v_ctx + N_slave p_ctxs)
            = 192 × (1 + 8)   # 8 EID 场景
            = 1728 个底层 udma_context

每个 udma_context 占用：
  - 1 个 USVA TID（或 1 个 SVA PASID 绑定）
  - 若干 jfc（每 jfc 占 max_jfc 配额之一 + CQE mmap）
  - 若干 jetty（占 max_jetty 配额之一）
  - pgdir/hugepage/page list（内存）
```

**待实测项（决定可行性，作为方案推进前置门禁）**：

| 待测项 | 查询方法 | 阈值要求 |
|---|---|---|
| ummu-core TID 池容量 | ummu-core 模块参数 / sysfs | ≥ 1728（sep 模式） |
| SVA PASID 容量 | IOMMU/设备 caps | ≥ 192（SVA per-mm，若同 mm 复用） |
| `udma_dev->caps.jetty.max_cnt` | `cat /sys/class/ubcore/<dev>/...` 或驱动 | ≥ 192 × 每容器 jetty 数 |
| `udma_dev->caps.jfc.max_cnt` | 同上 | ≥ 192 × 每容器 jfc 数 |
| 单 context 内存 footprint | 实测 | × 1728 ≤ 节点可用内存 |
| 建链 QPS（seg_tree 锁） | 压测 | 满足 192 容器并发拉起时延 |

3. `ubcore_free_ucontext` dec（[ubcore_device.c:1779](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L1779) 附近）：
   ```c
   atomic_dec(&dev->eid_table.eid_entries[ucontext->eid_index].users);
   ```
4. sysfs 新增 `eids/eidN/users` 节点（[ubcore_cdev_file.c](01_kernel/drivers/ub/urma/ubcore/ubcore_cdev_file.c)，仿 `eid_show_cb` :818）。

工作量：~2 人天，3 个文件，~50 行。**这是本场景唯一"为运维必须做的内核小改"**。

### 13.5 可选改（性能优化，按压测决定）

按 §4 路径 4，仅在压测暴露瓶颈时才做：

| 项 | 工作量 | 触发条件 |
|---|---|---|
| R2 lazy ldev 副本 | ★★★ | netns init 时延 > 容器拉起 SLA |
| R6/R-3 exit 异步化 + seg_tree 锁改 | ★★★★ | 滚动销毁或建链 QPS 不达标 |
| R-6 context 池化复用 | ★★★★ | HW 容量不足且无法扩容 |
| R5 per-cgroup 限速 | ★★ | 容器间流量互相干扰 |

这些是"锦上添花"，不影响 192 跑通，建议先压测再定。

### 13.6 工作量汇总（人天估算）

| 阶段 | 内容 | 人天 | 代码改动 |
|---|---|---|---|
| **阶段 0：前置实测** | R-1/R-2 HW 容量 + R4.3 选路压测 + R2/R6/R-3/R-7 性能压测 | 5-8 | 无 |
| **阶段 1：必须改** | R3 `/dev` 分发（device plugin）+ R1 shared 固化 + 监控 | 2-3 | 无内核 |
| **阶段 1'：uvs_api 对接**（外部模块入口，见 §14） | uvs_api 6 接口 + 用户态 TLV + 内核 UVS 6 handler/表项 | 4-6 | uvs 4 文件 + 内核 2 文件 ~200 行 |
| **阶段 2：应该改** | R4.2 per-EID users 计数（内核小改） | 2 | 3 文件 ~50 行 |
| **阶段 3：门禁扩容**（条件性） | R-1 TID 池扩容 / R-2 caps 调参（仅当实测不足） | 5-10 | ummu-core/udma |
| **阶段 4：可选优化**（条件性） | R2 lazy / R6 异步 / R-3 锁改 / R-6 池化 | 15-30 | 跨模块 |
| **合计（最小可行，无外部模块对接）** | 阶段 0 + 1 + 2 | **~10 人天** | 50 行内核 + 部署 |
| **合计（含 uvs_api 对接）** | 阶段 0 + 1 + 1' + 2 | **~14-16 人天** | 250 行（uvs+内核）+ 部署 |
| **合计（含优化）** | + 阶段 3 + 4 | **34-56 人天** | 视压测 |

> 阶段 1' 工作量拆解（§14）：uvs_api.h 声明 + tpsa_api.c 实现 + uvs_cmd_tlv.c TLV（用户态 ~120 行）+ ubcore_cmd.h 枚举 + ubcore_uvs_cmd.c 6 handler/表项（内核 ~80 行），共 ~200 行。内核 handler 仅转调已存在的 `ubcore_set_dev_ns_mode` 等，**不新增业务逻辑**。

### 13.7 关键结论

1. **框架层零改动即可让 192 容器共享 device/EID**：现有 `dev_sharing`/`eid_sharing` 三机制（[ubcore_device.c:79-92,1686,2522](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L79)）+ pernet 钩子已完备，**无需为"共享"本身改任何内核业务逻辑**。这是前期走读最关键的结论。
2. **唯一必须的代码外改动是 R3 `/dev` 分发**（部署侧，~1 人天），因为 uburma/ubagg class 非 netns-aware 是设计如此，靠 bind-mount 解决。
3. **唯一建议的内核小改是 R4.2 per-EID users 计数**（~2 人天，50 行），为运维可观测，非功能阻塞。
4. **外部模块对接需新增 uvs_api 接口**（§14，~4-6 人天，200 行）：6 个接口打通 UVS 通道（`/dev/ubcore` → `ubcore_uvs_cmd.c` 命令分发），内核 handler **转调已存在的 `ubcore_set_dev_ns_mode` 等**，不新增业务逻辑，与 `urma_admin` genl 入口等价、状态一致。
5. **真正的不确定性和潜在大工作量在 R-1/R-2 HW 容量**：必须先实测（max_jfc/max_jetty 已有 sysfs 可查，零代码；TID 池需查 ummu-core）。若实测 ≥ 1728 context 需求，则 192 场景最小可行 ~10 人天（不含 uvs）或 ~14-16 人天（含 uvs 对接）；若不足，则需阶段 3 扩容（5-10 人天）甚至阶段 4 池化复用（大改）。
6. **bonding 层无需改动**：`p_ctxs[20]` 非瓶颈（§9 已证），8 EID 远小于 20，192 容器各自独立 bonding context 不触限。

> **推进建议**：先做阶段 0 前置实测（5-8 人天，零代码），用 R-1/R-2 的实测结果决定后续是否需要阶段 3/4。若 HW 容量充足，192 场景落地：不含外部模块对接 ~10 人天（阶段 1 部署 + 阶段 2 可观测）；含 uvs_api 外部模块对接 ~14-16 人天（+阶段 1'）。阶段 1' 可与阶段 0/1 并行推进（独立于 HW 容量实测）。

> **补充**：若要求"由外部模块（编排系统/MXE 等管理面程序）调用 UVS 接口配置共享"，则需新增 §14 的 uvs_api 接口及其全链路实现，工作量见 §13.6 更新（阶段 1'）。

## 14. uvs_api 共享配置接口设计（外部模块对接）

### 14.1 背景与定位

前期走读确认：内核侧 `g_dev_ns_shared`/`g_eid_ns_shared` 开关 + expose/set_ns 等能力**已完备**（§2-§4），现有入口是 `urma_admin` 命令行（走 generic netlink `UBCORE_GENL`）。但编排系统、MXE 等外部管理面程序不直接 shell 调 `urma_admin`，而是链接 libuvs 走 **UVS 通道**（`/dev/ubcore` ioctl → 内核 `ubcore_uvs_cmd.c` 命令分发），这与 `urma_admin` 的 genl 通道是两条独立路径。

**诉求**：在 [uvs_api.h](00_umdk/umdk/src/urma/lib/uvs/core/include/uvs_api.h) 新增接口，让外部模块通过 UVS 库配置开启/关闭共享 eid、共享 device，以及精细化 expose/unexpose，使编排系统能在拉起 192 容器前程序化完成共享模式配置（对应 R1/R3 的控制面）。

### 14.2 现有 UVS 对接链路（来自走读）

```
外部模块
  └─ uvs_api.h: uvs_xxx()                      # 新接口在此声明
       └─ tpsa_api.c: uvs_xxx() 实现
            └─ uvs_cmd_tlv.c: uvs_ioctl_in_global(ctx, UVS_CMD_XXX, attrs)  # TLV 打包
                 └─ tpsa_ioctl.c: ioctl(ubcore_fd, TPSA_CMD, &hdr)         # /dev/ubcore
                      └─ 内核 ubcore_uvs_cmd.c: ubcore_uvs_global_cmd_parse()
                           └─ g_ubcore_uvs_global_cmd_funcs[UBCORE_CMD_XXX].func  # 命令分发表
                                └─ ubcore_cmd_xxx() handler
                                     └─ 转调 ubcore_set_dev_ns_mode/ubcore_set_eid_ns_mode/...  # 已存在
```

关键证据：
- 命令分发表 `g_ubcore_uvs_global_cmd_funcs[]`（[ubcore_uvs_cmd.c:392-408](01_kernel/drivers/ub/urma/ubcore/ubcore_uvs_cmd.c#L392)），加命令只需加一项。
- 分发入口 `ubcore_uvs_global_cmd_parse`（[:410](01_kernel/drivers/ub/urma/ubcore/ubcore_uvs_cmd.c#L410)），带 `need_cap_verify`（`CAP_NET_ADMIN`，[:421](01_kernel/drivers/ub/urma/ubcore/ubcore_uvs_cmd.c#L421)）。
- 命令枚举 `UBCORE_CMD_*` 在 [ubcore_cmd.h](01_kernel/drivers/ub/urma/ubcore/ubcore_cmd.h)（已有 `UBCORE_CMD_SET_DEV_NS_MODE` 等，但当前由 genl 用，UVS 表未收录）。
- 内核实现 `ubcore_set_dev_ns_mode`（[ubcore_device.c:2175](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2175)）/ `ubcore_set_eid_ns_mode`（[:2237](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2237)）/ `ubcore_expose_dev_ns`（[:2258](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2258)）/ `ubcore_set_dev_eid_ns`（[:2409](01_kernel/drivers/ub/urma/ubcore/ubcore_device.c#L2409)）均已存在，UVS handler 直接转调。

### 14.3 新增 uvs_api 接口

在 [uvs_api.h](00_umdk/umdk/src/urma/lib/uvs/core/include/uvs_api.h) 末尾（`#ifdef __cplusplus` 前）新增：

```c
/**
 * Namespace sharing mode for device / EID.
 */
typedef enum uvs_ns_sharing {
    UVS_NS_SHARING_OFF = 0,   /* exclusive: device/EID bound to its ns */
    UVS_NS_SHARING_ON  = 1,   /* shared: device/EID visible across all ns */
} uvs_ns_sharing_t;

/**
 * Set device namespace sharing mode (global switch g_dev_ns_shared).
 * Must be called before any container netns is created and before any
 * device is exposed. Switching shared->exclusive is rejected by kernel
 * if any netns exists (returns -EPERM).
 * @param[in] sharing  UVS_NS_SHARING_ON to enable global device sharing,
 *                      UVS_NS_SHARING_OFF to disable.
 * @return 0 on success, negative errno on error.
 */
int uvs_set_dev_ns_sharing(uvs_ns_sharing_t sharing);

/**
 * Set EID namespace sharing mode (global switch g_eid_ns_shared).
 * Independent from device sharing. When on, all EIDs are visible across
 * all netns; when off, each EID is visible only in its owning netns.
 * @param[in] sharing  UVS_NS_SHARING_ON / UVS_NS_SHARING_OFF.
 * @return 0 on success, negative errno on error.
 */
int uvs_set_eid_ns_sharing(uvs_ns_sharing_t sharing);

/**
 * Query current namespace sharing mode for device and EID.
 * @param[out] dev_sharing  current device sharing mode.
 * @param[out] eid_sharing  current EID sharing mode.
 * @return 0 on success, negative errno on error.
 */
int uvs_get_ns_sharing(uvs_ns_sharing_t *dev_sharing, uvs_ns_sharing_t *eid_sharing);

/**
 * Expose a device to a target network namespace (exclusive mode only).
 * Creates a logic-device sysfs copy of <dev_name> in the netns identified
 * by ns_path. Rejected if dev_sharing is ON (already globally visible).
 * @param[in] dev_name  device name (e.g. "bonding_dev0").
 * @param[in] ns_path   target netns path, "/proc/<pid>/ns/net" or
 *                      "/var/run/netns/<name>".
 * @return 0 on success, negative errno on error.
 */
int uvs_expose_dev_ns(const char *dev_name, const char *ns_path);

/**
 * Undo exposing a device from a target network namespace.
 * @param[in] dev_name  device name.
 * @param[in] ns_path   target netns path.
 * @return 0 on success, negative errno on error.
 */
int uvs_unexpose_dev_ns(const char *dev_name, const char *ns_path);

/**
 * Bind a single EID of a device to a target network namespace (exclusive
 * mode only). The device must already be exposed to that netns.
 * @param[in] dev_name  device name.
 * @param[in] eid_index EID index in the device's eid_table.
 * @param[in] ns_path   target netns path.
 * @return 0 on success, negative errno on error.
 */
int uvs_set_eid_ns(const char *dev_name, uint32_t eid_index, const char *ns_path);
```

设计要点：
1. **复用内核已存在能力**：所有接口最终转调 `ubcore_set_dev_ns_mode` 等，**不新增内核业务逻辑**，只打通 UVS 通道。
2. **语义与 `urma_admin` 对齐**：与 `urma_admin system set dev_sharing/eid_sharing`、`dev expose`、`eid set ... ns` 完全对应，同一套内核实现，两条入口（genl 给命令行，uvs 给程序）。
3. **`ns_path` 字符串入参**：与 `admin_get_ns_fd`（[admin_parameters.c:406](00_umdk/umdk/src/urma/tools/urma_admin/admin_parameters.c#L406)）一致的两种格式，由 uvs 用户态侧解析为 ns_fd 传内核（内核 `get_net_ns_by_fd` 已支持）。
4. **`uvs_ns_sharing_t` 枚举**：复用于 dev/eid 两个开关，简化外部模块调用。
5. **返回负 errno**：与 uvs 现有接口风格（返回 0/错误码）一致，便于外部模块判断 `-EPERM`（约束不满足）等。

```c
static int ubcore_cmd_set_dev_ns_sharing(struct ubcore_global_file *file,
                                        struct ubcore_cmd_hdr *hdr)
```

### 14.5 与现有 genl 入口的关系

| 入口 | 通道 | 调用方 | 适用 |
|---|---|---|---|
| `urma_admin`（genl `UBCORE_GENL`） | netlink | 运维人员命令行 | 人工运维、脚本 |
| **新增 `uvs_xxx`**（UVS `/dev/ubcore`） | ioctl | 外部模块/编排系统 | 程序化配置、容器编排集成 |

两者**共用同一套内核实现**（`ubcore_set_dev_ns_mode` 等），互不冲突，状态一致（都读写同一对全局开关）。外部模块按 §14.3 调 uvs 接口，等价于执行 `urma_admin system set dev_sharing on`。

### 14.6 典型调用时序（编排系统拉起 192 容器前）

```c
/* 外部编排模块，节点初始化阶段（容器拉起前，无自定义 netns 存在） */
int setup_urma_sharing(void) {
    /* 1. 开启全局共享（device + EID） */
    if (uvs_set_dev_ns_sharing(UVS_NS_SHARING_ON) != 0)  return -1;
    if (uvs_set_eid_ns_sharing(UVS_NS_SHARING_ON) != 0)  return -1;

    /* 2. 校验生效 */
    uvs_ns_sharing_t dev, eid;
    uvs_get_ns_sharing(&dev, &eid);
    if (dev != UVS_NS_SHARING_ON || eid != UVS_NS_SHARING_ON)  return -1;

    /* 3. 此后拉起 192 容器（各 netns 创建时内核自动建 sysfs ldev 副本） */
    /*    容器内 bind-mount /dev/uburma/* + /dev/ubagg（见 R3 部署） */
    return 0;
}
```

精细化暴露路径（exclusive 模式，可选）：

```c
/* 把 bonding_dev0 + 其 EID idx=2 暴露到容器 ns（容器 pid 已知） */
char ns[64]; snprintf(ns, sizeof(ns), "/proc/%d/ns/net", ctr_pid);
uvs_expose_dev_ns("bonding_dev0", ns);
uvs_set_eid_ns("bonding_dev0", 2, ns);
```

### 14.7 约束与错误处理

| 场景 | 内核返回 | 外部模块处理 |
|---|---|---|
| shared→exclusive 时已有 netns | `-EPERM` | 先销毁所有容器 netns 再切 |
| exclusive→shared 时有 device 已 expose | `-EPERM` | 先 `uvs_unexpose_dev_ns` 全部 |
| shared 模式下调 `uvs_expose_dev_ns` | `-EPERM` | shared 已全可见，不应调 expose |
| `ns_path` 格式错误 | `-EINVAL` | 用户态侧 `urma_validate_ns_path` 校验（[admin_parameters.c:343](00_umdk/umdk/src/urma/tools/urma_admin/admin_parameters.c#L343)） |
| 非 `CAP_NET_ADMIN` | `-EPERM` | 编排进程需具备该 cap |

### 14.8 接口设计小结

- **6 个新接口**：`uvs_set_dev_ns_sharing` / `uvs_set_eid_ns_sharing` / `uvs_get_ns_sharing` / `uvs_expose_dev_ns` / `uvs_unexpose_dev_ns` / `uvs_set_eid_ns`。
- **全链路复用现有实现**：内核侧不新增业务逻辑，只打通 UVS 命令通道（6 个 handler + 表项 + TLV）。
- **与 genl 入口等价**：同一套内核开关，两条入口，状态一致。
- **面向外部模块**：让编排系统/MXE 程序化配置共享，无需 shell 调 `urma_admin`。
